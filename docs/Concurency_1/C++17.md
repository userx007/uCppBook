# C++17 Concurrency: What's New

C++17 made more meaningful concurrency additions than C++14 did, though the biggest leap (coroutines, `jthread`, `latch`/`barrier`, atomic `shared_ptr`) was still to come in C++20. This guide covers only what's *new* in C++17, on top of everything from C++11/C++14.

Compile with: `g++ -std=c++17 -pthread file.cpp` (parallel algorithms may additionally need `-ltbb` on GCC/Clang, since they're commonly implemented via Intel TBB).

---

## 1. `std::shared_mutex` — Reader/Writer Lock (Non-Timed)

Header: `<shared_mutex>`

C++14 gave you `std::shared_timed_mutex`. C++17 adds a lighter-weight sibling, `std::shared_mutex`, which drops the timed-locking operations (`try_lock_for`/`try_lock_until`). If you don't need timeouts, prefer this — implementations can make it cheaper than the timed version.

```cpp
#include <shared_mutex>
#include <thread>
#include <iostream>

std::shared_mutex rw_mutex;
int shared_data = 0;

void reader(int id) {
    std::shared_lock<std::shared_mutex> lock(rw_mutex); // shared/read lock
    std::cout << "Reader " << id << " sees " << shared_data << "\n";
}

void writer(int value) {
    std::lock_guard<std::shared_mutex> lock(rw_mutex);  // exclusive/write lock
    shared_data = value;
}

int main() {
    std::thread w(writer, 42);
    w.join();
    std::thread r1(reader, 1), r2(reader, 2);
    r1.join(); r2.join();
}
```

Supported operations: `.lock()`/`.unlock()` (exclusive), `.lock_shared()`/`.unlock_shared()` (shared), `.try_lock()`/`.try_lock_shared()` (non-blocking). `std::shared_lock` (from C++14) is used the same way as before as its RAII wrapper.

**Rule of thumb:** use `shared_mutex` unless you specifically need `try_lock_for`/`try_lock_until`, in which case use `shared_timed_mutex`.

## 2. `std::scoped_lock` — Variadic Deadlock-Free RAII Lock

Header: `<mutex>`

In C++11, locking multiple mutexes safely required this two-step dance:

```cpp
// C++11 way
std::lock(m1, m2);
std::lock_guard<std::mutex> lk1(m1, std::adopt_lock);
std::lock_guard<std::mutex> lk2(m2, std::adopt_lock);
```

`std::scoped_lock` collapses that into one line. It accepts any number of mutexes (including zero or one), locks them all using the same deadlock-avoidance algorithm as `std::lock`, and releases them all on destruction.

```cpp
#include <mutex>

std::mutex m1, m2;

void transfer() {
    std::scoped_lock lock(m1, m2); // locks both, deadlock-free, class template argument deduction (CTAD)
    // ... safe to use both resources ...
} // both unlocked automatically
```

With a single mutex it behaves just like `lock_guard`:

```cpp
std::mutex m;
void critical_section() {
    std::scoped_lock lock(m); // equivalent to lock_guard<mutex> here
    // ...
}
```

Prefer `scoped_lock` over the manual `std::lock` + `adopt_lock` pattern whenever you're locking two or more mutexes together — it's shorter and just as safe.

## 3. Parallel Algorithms (Execution Policies)

Header: `<execution>` (policies), used with existing `<algorithm>`/`<numeric>` functions

C++17's biggest concurrency-adjacent addition: most standard algorithms (`sort`, `for_each`, `transform`, `reduce`, `find`, etc.) got overloads that accept an **execution policy** as their first argument, letting the implementation parallelize and/or vectorize the work — no manual thread management required.

```cpp
#include <algorithm>
#include <execution>
#include <vector>
#include <numeric>

int main() {
    std::vector<int> v(1'000'000);
    std::iota(v.begin(), v.end(), 0);

    // Sort using multiple threads, chosen by the implementation
    std::sort(std::execution::par, v.begin(), v.end(), std::greater<int>());

    // Sum in parallel
    long long total = std::reduce(std::execution::par, v.begin(), v.end(), 0LL);

    // Apply a function to every element, in parallel
    std::for_each(std::execution::par, v.begin(), v.end(), [](int& x) { x *= 2; });
}
```

Execution policies:

- `std::execution::seq` — sequential, no parallelism (same as calling without a policy, but documents intent).
- `std::execution::par` — parallel: the algorithm may run across multiple threads. Your callable must be safe to call concurrently from different threads (no unsynchronized shared-state mutation).
- `std::execution::par_unseq` — parallel *and* vectorized: the algorithm may interleave operations on a single thread (SIMD) as well as run across threads. Your callable must not do things unsafe under vectorization, such as acquiring locks or allocating memory in some implementations.

```cpp
// A reduction that also uses vectorization
double sum = std::reduce(std::execution::par_unseq, data.begin(), data.end());
```

This is a fundamentally different concurrency model from `std::thread`/`std::async` — you don't manage threads directly; you describe *what* can run in parallel and the implementation decides *how*.

## 4. `std::atomic<T>::is_always_lock_free`

Header: `<atomic>`

A `static constexpr bool` member added to `std::atomic` in C++17. Unlike the existing (C++11) runtime `.is_lock_free()` member function, this is a compile-time constant telling you whether the type is guaranteed lock-free on *every* target the code might run on — useful for `static_assert`s and compile-time branching.

```cpp
#include <atomic>

static_assert(std::atomic<int>::is_always_lock_free,
              "This platform doesn't guarantee lock-free int atomics");

std::atomic<int> counter{0};
if constexpr (std::atomic<int>::is_always_lock_free) {
    // compile-time branch: no need for a fallback locking path
}
```

Compare with the older, runtime-only check from C++11:

```cpp
std::atomic<int> a{0};
bool lock_free_here = a.is_lock_free(); // known only at runtime, on this specific machine
```

## 5. `std::hardware_destructive_interference_size` / `std::hardware_constructive_interference_size`

Header: `<new>`

Not a synchronization primitive, but directly relevant to concurrent code performance: these two `constexpr` values help you avoid **false sharing** — where independent atomics/variables used by different threads happen to sit on the same cache line, causing needless cache-coherency traffic.

```cpp
#include <new>
#include <atomic>

struct alignas(std::hardware_destructive_interference_size) PaddedCounter {
    std::atomic<int> value{0};
    // padding to hardware_destructive_interference_size prevents this
    // struct from sharing a cache line with a neighboring PaddedCounter
};

PaddedCounter counters[4]; // each thread hammers a different counters[i] without false sharing
```

- `hardware_destructive_interference_size` — minimum recommended offset between two objects to *avoid* false sharing (pad structs to this size when different threads write to adjacent fields).
- `hardware_constructive_interference_size` — maximum recommended size for objects that *should* share a cache line (group data that's read together by the same thread).

## Quick Summary Table

| Element | Header | Purpose |
| --- | --- | --- |
| `std::shared_mutex` | `<shared_mutex>` | Reader/writer lock, no timed-locking overhead |
| `std::scoped_lock` | `<mutex>` | Variadic, deadlock-free RAII lock for 0+ mutexes |
| Execution policies (`seq`, `par`, `par_unseq`) | `<execution>` | Parallelize/vectorize standard algorithms |
| `atomic<T>::is_always_lock_free` | `<atomic>` | Compile-time lock-free guarantee check |
| `hardware_destructive_interference_size` / `hardware_constructive_interference_size` | `<new>` | Cache-line sizing to avoid/encourage false sharing |

---

**Context:** `std::shared_timed_mutex`/`shared_lock` (C++14) still exist and are useful when you need timeouts. C++20 later added `std::jthread`, `std::latch`, `std::barrier`, `std::counting_semaphore`, atomic `wait`/`notify`, and atomic `shared_ptr` — a much larger concurrency expansion than either C++14 or C++17.
