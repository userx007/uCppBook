# C++23 Concurrency: What's New

After the huge C++20 expansion, C++23 is a quiet release for concurrency — much like C++14 was after C++11. There are no new synchronization primitives (no new mutex, latch, barrier, or semaphore types). The two real additions are: a ready-made coroutine-based generator type (finishing off a gap C++20 deliberately left open), and a C-interop header for atomics. One more thing (`std::move_only_function`) isn't a concurrency feature per se, but is genuinely useful in concurrent code, so it's included.

Compile with: `g++ -std=c++23 -pthread file.cpp` (as of late 2025/2026, compiler/standard-library support for `<generator>` specifically is still uneven — check your toolchain).

---

## 1. `std::generator` — Ready-Made Coroutine Generator

Header: `<generator>`

The C++20 guide showed that coroutines only gave you the low-level machinery (`co_yield`, `std::coroutine_handle`) — you had to hand-write a promise type to get a usable generator. C++23's `std::generator<T>` is exactly that ready-made type, so you no longer write your own.

```cpp
#include <generator>
#include <iostream>

std::generator<int> count_up_to(int n) {
    for (int i = 1; i <= n; ++i)
        co_yield i;   // suspends, produces i, resumes on the next iteration
}

int main() {
    for (int value : count_up_to(5)) // range-based for works directly on a generator
        std::cout << value << " ";   // prints: 1 2 3 4 5
}
```

Compare this to the \~20 lines of hand-written `promise_type` boilerplate the same generator needed in C++20 — `std::generator` removes that entirely for the common case of "a coroutine that lazily yields a sequence of values."

Like coroutines in general, `std::generator` by itself doesn't imply multithreading — it's about lazy, suspendable computation on a single thread. Its concurrency relevance is the same as C++20 coroutines: it's a cleaner building block for writing asynchronous or lazily-evaluated code that can be combined with scheduling/async-I/O libraries.

```cpp
// Infinite generator, consumed lazily — useful for streaming/async-style pipelines
std::generator<int> naturals() {
    for (int i = 0; ; ++i)
        co_yield i;
}

int main() {
    int count = 0;
    for (int n : naturals()) {
        std::cout << n << " ";
        if (++count == 5) break; // stops pulling values; no infinite loop actually runs
    }
}
```

## 2. `<stdatomic.h>` — C11 Atomics Compatibility Header

Header: `<stdatomic.h>`

C++23 adds this header purely for interoperability with C code that uses C11's `<stdatomic.h>` atomics. It defines type aliases like `atomic_int`, `atomic_bool`, `atomic_size_t` as synonyms for the corresponding `std::atomic<T>` specializations, plus macros like `ATOMIC_VAR_INIT`, so headers shared between C and C++ translation units can use the same atomic type names in both languages.

```cpp
#include <stdatomic.h> // C++23: now works in C++ too, aliasing std::atomic

atomic_int counter = 0;  // equivalent to std::atomic<int> counter{0};

void increment() {
    atomic_fetch_add(&counter, 1); // C-style free-function atomic API, also supported
}
```

This isn't a new capability for C++ programs (you already had `std::atomic<int>`) — it exists so that a header included from both a `.c` file and a `.cpp` file can use identical syntax. If you're writing pure C++ concurrency code, you can keep using `std::atomic<T>` directly; reach for this header only when sharing atomic-using code with C.

## 3. `std::move_only_function` — Move-Only Callable Wrapper (Adjacent, Not New Concurrency Itself)

Header: `<functional>`

Not a concurrency primitive, but frequently the missing piece when building thread pools, task queues, or callback-based async code. `std::function` requires its target to be **copyable**, which is a problem for tasks that capture move-only state (like a `std::unique_ptr` or a `std::promise`). `std::move_only_function` drops that requirement.

```cpp
#include <functional>
#include <memory>
#include <queue>
#include <mutex>

std::mutex queue_mtx;
std::queue<std::move_only_function<void()>> task_queue;

void submit_task(std::unique_ptr<int> owned_data) {
    std::lock_guard<std::mutex> lock(queue_mtx);
    // Capturing a unique_ptr by move — impossible with std::function, fine here
    task_queue.push([data = std::move(owned_data)]() mutable {
        // ... use *data ...
    });
}

void run_next_task() {
    std::move_only_function<void()> task;
    {
        std::lock_guard<std::mutex> lock(queue_mtx);
        if (task_queue.empty()) return;
        task = std::move(task_queue.front());
        task_queue.pop();
    }
    task(); // invoke outside the lock
}
```

Before C++23, thread pool implementations either wrapped move-only captures in a `shared_ptr` to satisfy `std::function`'s copyability requirement, or wrote a custom callable wrapper. `std::move_only_function` removes that workaround.

## What Did *Not* Make It Into C++23

Worth calling out explicitly, since it's easy to expect otherwise: the senders/receivers proposal (`std::execution`, P2300) — a major new asynchronous-programming and structured-concurrency model, roughly analogous to what `std::future`/`async` do but far more composable and efficient — was **not** merged into C++23. It's targeted for **C++26**. If you see references to `std::execution::sender`, task schedulers, or "P2300," that's upcoming, not currently standard.

## Quick Summary Table

| Element | Header | Purpose |
| --- | --- | --- |
| `std::generator<T>` | `<generator>` | Ready-made coroutine-based lazy generator type |
| `<stdatomic.h>` (`atomic_int`, etc.) | `<stdatomic.h>` | C11-atomics-compatible aliases for `std::atomic<T>` |
| `std::move_only_function` | `<functional>` | Callable wrapper supporting move-only captures (useful for task queues) |

---

**Context:** C++23 intentionally left the big structured-concurrency model (senders/receivers, `std::execution`) for C++26. If your work depends on a richer async-task model than `std::future`/`std::async`/coroutines currently give you, that's the standard to watch next, alongside any incremental refinements to `jthread`/`stop_token` that may land alongside it.
