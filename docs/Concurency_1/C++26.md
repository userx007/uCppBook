# C++26 Concurrency: What's New

C++26 is the largest concurrency release since C++11 introduced threading at all — bigger even than C++20. Its headline feature is `std::execution` (senders/receivers, from proposal P2300), a completely new structured-asynchrony model meant to eventually sit alongside (and in many new codebases, replace) `std::async`/`std::future`/callback-based concurrency. Alongside it, C++26 adds two classic lock-free memory-reclamation techniques as standard facilities: hazard pointers and RCU (read-copy-update).

**Status note (as of September 2026):** the C++26 working draft is complete and the final standard is expected to be formally published later in 2026. GCC and Clang have implemented most of these features during standardization, but library support — especially for `std::execution` — is still landing and in places experimental; check your specific toolchain version before relying on this in production. Everything from C++11 through C++23 carries forward unchanged; this guide covers only what's new.

## 1. `std::execution` — Senders/Receivers (P2300)

Header: `<execution>`

This is the big one. `std::execution` is a general-purpose framework for describing asynchronous and parallel work as composable, lazy chains — instead of eagerly starting work like `std::async` does, or manually wiring up mutexes/condition variables/futures. It's designed to work efficiently across very different execution contexts: thread pools, GPUs, and non-blocking I/O, all through the same vocabulary.

Three core abstractions:

- **Scheduler** — a lightweight handle to an execution resource (a thread pool, an I/O context, a GPU queue).
- **Sender** — describes a unit of asynchronous work that hasn't started yet, and will eventually complete with a value, an error, or "stopped."
- **Receiver** — the recipient that gets notified when a sender completes.

```cpp
#include <execution>
#include <iostream>

int main() {
    using namespace std::execution;

    // Assume 'pool' is some thread pool providing a scheduler
    auto sch = pool.scheduler();

    sender auto begin  = schedule(sch);                          // start a chain of work on 'sch'
    sender auto hello  = then(begin, [] {                        // 'then' chains a callable onto the sender
        std::cout << "Hello from the pool\n";
        return 13;
    });
    sender auto add_42 = then(hello, [](int x) { return x + 42; }); // compose further, still nothing has run yet

    auto [result] = this_thread::sync_wait(add_42).value();      // NOW the whole chain actually executes
    std::cout << "Result: " << result << "\n";                   // 55
}
```

Nothing runs until something actually consumes the sender (here, `sync_wait`) — this laziness is what lets the library fuse operations together and avoid the allocations and overhead that eager futures/callbacks tend to accumulate.

### Key algorithms

```cpp
using namespace std::execution;

// Run several senders concurrently, wait for all of them
sender auto combined = when_all(
    then(schedule(sch), [] { return 1; }),
    then(schedule(sch), [] { return 2; })
);
auto [a, b] = this_thread::sync_wait(combined).value(); // a == 1, b == 2

// Chain based on a value produced earlier, choosing the next sender dynamically
sender auto conditional = let_value(schedule(sch), [] {
    return then(schedule(sch), [] { return 99; }); // returns a new sender based on runtime logic
});
```

- `schedule(sch)` — a sender that completes on a given scheduler.
- `then(sender, fn)` — runs `fn` with the previous sender's result, producing a new sender.
- `when_all(senders...)` — runs multiple senders concurrently, completes once all finish.
- `let_value(sender, fn)` — lets `fn` return a brand-new sender based on the prior result (dynamic composition).
- `sync_wait(sender)` — blocks the calling thread, actually executing the chain, and returns the result.

### Coroutine interop

Senders are designed to compose naturally with C++20 coroutines — you can `co_await` a sender directly inside a coroutine, and a coroutine itself can be treated as a sender:

```cpp
#include <execution>

std::execution::task<int> compute(std::execution::scheduler auto sch) {
    co_await std::execution::schedule(sch);      // suspend, resume running on 'sch'
    int x = co_await some_async_operation();     // await another sender-based operation
    co_return x + 1;
}
```

### Structured concurrency helpers

C++26 also brings supporting pieces that round out `std::execution` into something usable for real programs:

- **`async_scope`** — manages a group of concurrently-running senders as a unit, ensuring none of them outlive the scope (structured lifetime management, similar in spirit to structured concurrency in other languages).
- **`std::execution::run_loop`** / a **system execution context** — a standard, always-available scheduler backed by a simple thread pool, so code doesn't need a third-party thread-pool library just to get started.
- **Parallel scheduler** — a scheduler tuned for CPU-bound parallel work, intended to interoperate with the `<execution>` policies (`par`, `par_unseq`) already used by C++17's parallel algorithms.

The overall goal, in the committee's own framing, is to make it far easier to write concurrent and parallel code that is "data-race-free by construction" through structured, lifetime-nested composition — rather than manually tracking which threads own which mutexes and when futures get destroyed.

## 2. `std::hazard_pointer` — Lock-Free Memory Reclamation

Header: `<hazard_pointer>`

Solves the "safe reclamation problem" in lock-free data structures: if one thread removes a node from a lock-free structure (e.g., a lock-free stack) and deletes it, another thread that already grabbed a raw pointer to that node before the removal might still be reading it — a use-after-free. Hazard pointers let a reader "declare" it's using a pointer, so a writer knows not to actually free that memory yet.

```cpp
#include <hazard_pointer>
#include <atomic>

template <typename T>
struct Node : std::hazard_pointer_obj_base<Node<T>> { // must derive from this base
    T value;
    Node* next;
};

std::atomic<Node<int>*> head;

// Reader thread: safely read the current head, protected from concurrent deletion
int read_head_safely() {
    std::hazard_pointer hp = std::make_hazard_pointer(); // register a hazard pointer
    Node<int>* p = hp.protect(head);                     // atomically load + protect
    int result = p ? p->value : -1;                      // safe to dereference 'p' here
    return result;                                       // hp releases protection when it goes out of scope
}

// Writer thread: remove the head node and retire it (deferred deletion)
void pop_head() {
    Node<int>* old_head = head.load();
    if (old_head && head.compare_exchange_strong(old_head, old_head->next)) {
        old_head->retire(); // deletion deferred until no hazard pointer protects it
    }
}
```

This is the standardized version of a pattern already used in production for years by libraries like Facebook's Folly — now available without a third-party dependency, and usable for building your own lock-free queues, stacks, or hash tables.

## 3. RCU (Read-Copy-Update)

Header: `<rcu>`

The other classic lock-free reclamation technique, standardized alongside hazard pointers. RCU optimizes heavily for the read-mostly case: readers access shared data with essentially no synchronization overhead (no atomics on the read path at all, in the common case), while writers create a new copy of the data, publish it atomically, and defer destruction of the old copy until all readers that might still be using it have finished.

```cpp
#include <rcu>
#include <atomic>
#include <memory>

std::rcu_domain domain; // coordinates readers and writers
std::atomic<Config*> current_config;

// Reader: extremely low overhead, no locks
void handle_request() {
    std::rcu_domain::rcu_retire_guard guard(domain); // marks start of a read-side critical section
    Config* cfg = current_config.load(std::memory_order_acquire);
    // ... use *cfg freely; guaranteed not to be freed while guard is alive ...
} // guard destructor marks the end of the read-side critical section

// Writer: publish a new version, defer cleanup of the old one
void update_config(Config* new_cfg) {
    Config* old_cfg = current_config.exchange(new_cfg, std::memory_order_acq_rel);
    domain.rcu_retire(old_cfg); // freed only after all in-flight readers finish
}
```

**Hazard pointers vs. RCU, in short:** hazard pointers track protection per-pointer and are usually cheaper when only specific pointers need protecting; RCU protects an entire read-side critical section at near-zero cost per read but can delay reclamation longer and traditionally suits scenarios with many more reads than writes (e.g., rarely-changing configuration data, routing tables). Both exist in the standard now so you can pick whichever fits your access pattern instead of reaching for an external library.

## Quick Summary Table

| Element | Header | Purpose |
| --- | --- | --- |
| `std::execution` (senders, receivers, schedulers) | `<execution>` | Structured, composable asynchronous/parallel execution model |
| `then`, `when_all`, `let_value`, `sync_wait`, etc. | `<execution>` | Core sender algorithms for composing async work |
| `async_scope` | `<execution>` | Structured lifetime management for groups of senders |
| System execution context / parallel scheduler | `<execution>` | Standard, ready-to-use schedulers (general + CPU-parallel) |
| `std::hazard_pointer` | `<hazard_pointer>` | Per-pointer lock-free memory reclamation |
| RCU (`std::rcu_domain`, `rcu_retire`, etc.) | `<rcu>` | Read-side-cheap lock-free memory reclamation |

---

**Context:** `std::execution` has been in development since around 2015 in various forms (executors, then senders/receivers) and was formally adopted for C++26 in June 2024. It's intended as a long-term foundation — future standards are expected to build networking and other async I/O facilities on top of it, rather than introducing yet another separate async model.
